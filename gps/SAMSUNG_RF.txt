SM-A300FU GNSS compatibility
===========================

Assistance and satellite reports
-------------------------------
The device config restores the stock MSB/MSA capability bits (0x37) and
SUPL_MODE=3. Without both capability bits, loc_eng_set_position_mode forces
standalone and the SUPL state machine is not created. PSDS URLs retain the
Android 12 LONGTERM_PSDS_SERVER names and HTTPS; copying the old stock HTTP
XTRA_SERVER names would not configure the Android 12 downloader.

Keep the proprietary libloc_api_v02 HaxxSvStatus ABI intact (672 bytes on ARM).
Convert it at the framework callback boundary, preserving the separate GPS,
GLONASS and 64-bit BeiDou used-in-fix masks. Use gnss_sv_status_cb when present;
copy to a correctly sized legacy GpsSvStatus otherwise. Only GPS has ephemeris
and almanac masks in this ABI; do not invent these flags for other systems.
C/N0, elevation and azimuth are copied without gain offsets. This conversion
does not remove the proprietary input's 32-SV limit.

Samsung RF selector
-------------------
Evidence: A300FU Android 5 BPE1/BOJ4 and Android 6 CSG3 stock AP libraries,
plus the running A300FUXXU1BOEC modem image. No firmware or NV was patched.

The stock libgps.utils configuration table maps GNSS_RF_CONFIG to offset 0x88
in sec_gps_conf. Its initialization writes 1. libloc_eng forwards the setting
through LocApiV02::setGnssRfConfig to SECGPS, a private QMI v1 service 0xe8.

Message 9 has a one-byte request and one-byte reply, each mandatory TLV 1.
Stock request: 01 01 00 01. Success reply: 01 01 00 00. The decoder treats a
nonzero response as failure and rejects malformed, duplicate or missing TLVs;
the stock C++ wrapper instead discarded the transport result.

The modem's QMI_SECGPS_SET_GLONASS_ENABLE handler (physical image address
0x8752b3b0) logs "GNSS RF setting from AP" and passes the selector to PDSM
parameter 0x2c. It preserves selectors 0, 1, 3 and 7, mapping other values to 7.
It replies 0 after the parameter request is accepted, and 0xff on failure.
This is a GNSS RF/configuration selector, not a gain, GPIO or voltage value.
The exact physical meaning of every nondefault mode is not established.
The implementation intentionally sends only the confirmed board default 1;
it does not expose arbitrary modes or claim increased antenna gain.

Use CCI's raw API, retaining only IDL service-discovery metadata. Validate the
library's service ID/version accessors before connecting. No guessed codec
tables or proprietary C++ vtable changes are required. Discovery and requests
have bounded timeouts. Failure is logged and must not stop ordinary GNSS.

Apply from the serialized start handler, including its engine-up/SSR recovery
path, before startFix. Compile this hook only for TARGET_DEVICE=a3lte.

IPC Router defaults unknown services to NET_RAW. Stock loc_launcher had that
group; the current GNSS HAL does not. sec_config grants only the gps group
access to service 232, rather than granting NET_RAW or weakening the default.
init creates gpsone_d for the legacy assistance pipes, with location-data
labeling inherited from /data/misc/location.

Validation
----------
Build optional a3_gnss_sv_test and a3_gnss_rf_test (not product packages).
Run both without arguments for conversion/protocol regression cases.
Build a3_gnss_psds_test for a separate injection-only integration test. It takes
an existing downloaded XTRA3 binary, sends it through the actual HIDL extension,
and reports queue acceptance. LocEngInjectXtraData logs the adapter return;
the proprietary adapter can return success even after a modem rejection, so
check its QMI indication log as well. Queue/adapter success is not proof of
a successful modem transaction.
RF test --discover only opens/releases SECGPS; it sends no RF request.
RF test --apply-stock sends exactly the default 1 and requires its modem ACK.
Also validate the production HAL under the gps UID: root discovery/request
success alone does not test IPC Router permissions.

GnssSessionProbe.java is an optional 30-second app_process client. Compile
against framework-minus-apex.jar and dex with d8, then run from a root ADB
shell with its dex in CLASSPATH. It drops the client to system UID so that
the package android matches LocationManager's identity validation. It prints
only counts, used masks, C/N0, elapsed time and accuracy, never coordinates.
It removes listeners after testing and does not delete aiding data.
Optional --assist uses Android 12 force_psds_injection and requests fresh
PSDS and time injection without deleting
existing assistance. Request acceptance alone does not prove modem injection.

Live validation can replace the two libraries and device GPS config, then
restart only vendor.gnss_service. Refresh any gps_debug.conf bind mount after
atomically replacing gps.conf, or the framework may keep the old inode.
Apply only the new IPC rule for a live test; do not duplicate existing rules.
Do not reboot merely to apply these changes.

A short indoor session and synthetic conversion cases establish integration,
not stock-equivalent TTFF, RF sensitivity, or all constellation configurations.
Modem SSR recovery is covered by the shared source path, not destructive SSR
fault injection during device validation.

Deployment observations (2026-10-20)
----------------------------------
The phone's network resolves legacy xtrapath*.izatcloud.net to Oregon servers
whose TLS leaf certificate expired in 2022. Public DNS from the workstation
resolves those names to a CDN with a current certificate. A diagnostic request
to that CDN from the phone, retaining the proper SNI and TLS verification,
returns HTTP 403 explicitly stating that access from this country is blocked.
Do not pin CDN IPs, disable certificate verification, or silently substitute
unknown assistance providers. These external failures can prevent automatic
PSDS downloads despite working HAL support. Mobile data is disabled on this
phone; Android rejects the SUPL cellular network request for that reason.
Neither user setting nor network DNS is changed by these patches.
The framework's "Unable to initialize IGnssXtra interface" info message is
misleading in this source version: its branch logs it after successful callback
registration. Do not interpret that line alone as an extension failure.

Direct injection of current HTTPS-downloaded xtra3grc.bin and xtra2.bin through
the production HIDL extension reaches the modem, which rejects the last chunk
with eQMI_LOC_INVALID_PARAMETER_V02 despite eLOC_CLIENT_SUCCESS transport.
The current and stock Android 6 setXtraData implementations both send message
0x35, 1024-byte chunks and the same format selector. Do not report PSDS as
end-to-end restored merely because the HAL queued it. Current assistance data
compatibility with the old BOEC modem is unresolved; no modem firmware is
flashed and no aiding data is deleted during these tests.

PSDS follow-up (2026-10-20)
--------------------------
Direct HTTPS downloads from the phone in Belarus succeeded for:
  https://xtrapath9.izatcloud.net/xtra3grc.bin (27504 bytes)
  https://xtrapath10.izatcloud.net/xtra3grc.bin (34335 bytes)
Both use normal hostname/certificate verification. Configure only these two
LONGTERM_PSDS_SERVER entries; do not randomly select a known failing endpoint.
The GrapheneOS Qualcomm cache is reachable but only serves xtra3Mgrbeji.bin;
its newer format is rejected by this BOEC modem and is not a usable fallback.
Do not substitute Broadcom/Samsung PSDS formats for Qualcomm XTRA.

Stock Samsung also has secgps_set_xtra_enable: SECGPS v1 message 8, mandatory
TLV 1 byte 1, reply TLV 1 byte 0 on accepted request. Its modem handler at
0x8752b2f0 forwards the Boolean to PDSM parameter 0x2b. This is distinct from
RF selector message 9 / parameter 0x2c. Apply the confirmed enable operation
before injecting orbit data, only on a3lte. A successful enable ACK does not
establish that the subsequent orbit data was accepted.

The optional a3_gnss_psds_status probe defaults to a read-only LOC 0x37 query.
It uses the real loc_qmi_idl_service_object_v02 exported by the existing blob
and CCI raw TLVs. It reports the indication status and modem validity interval.
--inject FILE explicitly sends LOC 0x35 parts and checks each modem status and
part acknowledgement, bypassing HIDL, libloc_eng and the blob's injection code.
--inject-xtra3 FILE tests LOC 0xa7 without the old format-type TLV; BOEC does not
return its indication. No aiding-data deletion is performed by these probes.
Wire field definitions are independently described in libqmi's LOC schema:
https://github.com/linux-mobile-broadband/libqmi/blob/main/data/qmi-service-loc.json

The normal XTRA3 file still fails at the final part even with raw QMI, matching
the proprietary adapter's failure; modem-reported duration remains zero.
The private XTRA enable operation is accepted but does not fix that rejection.
UTC aiding corrects a 1024-week epoch discrepancy observed in the old modem's
validity report, but does not itself make the data valid. Do not claim this
proves the precise cause of the parser failure or stock-equivalent operation.
CQI1 CP firmware from the supplied Android 6 CSG3 archive has been extracted
for a separately authorized compatibility test. BOEC remains installed; no
direct writes to modem, EFS or NV partitions are performed by these changes.

BOEC library/firmware comparison (2026-10-20)
-------------------------------------------
Offline inspection of the actual LOC IDL tables establishes the following:
                         BOEC       stock Android 5  current blob  stock Android 6
LOC minor version        29         33               44            48
LOC 0x35 request struct   1044       1044             1044          1044
LOC 0x35 maximum wire     1053       1053             1053          1053
LOC 0x35 indication       8          8                8             8
The meaningful request descriptor bytes are identical in all four images:
  01020002010403010604700c000404c410821004
The indication descriptor is also identical: 010200c2100106.
Different LOC minor versions do not imply an incompatible 0x35 wire schema.

LOC 0x37 validity refers to aggregate index 23 on BOEC and 25 in the AP blobs.
These are equivalent aggregates: 16-byte native struct, descriptor 0300010820,
with uint64 UTC seconds and uint16 duration hours. Native struct padding is
not part of the 10-byte wire aggregate. UTC injection 0x38 also has identical
request/indication descriptors in all four images. Do not reinterpret the
validity timestamp as milliseconds or the aggregate index as a format change.

Both supplied stock gps.conf files and BOEC's embedded URLs name xtra3grc.bin.
This rules out a blanket claim that BOEC was designed only for xtra.bin.
It does not prove compatibility with every current file served at that name.
The AP setXtraData implementations copy the payload unchanged into 1024-byte
parts, including the actual short final part, with format selector 0. There
is no observed stock-specific padding, decompression or terminal command.
The current and Android 5 IDL encoders were additionally compared byte for
byte with raw TLVs at final payload lengths 1, 512, 1023 and 1024: all matched.

A full matching Android 5 library-set probe submitted a 27504-byte file and
received INVALID_PARAMETER at part 27, while its public API returned 0.
However, the saved log also shows the normal GNSS service running concurrently
(PID 2049 alongside stock probe PID 2042), plus ENGINE_BUSY/timeouts during
configuration. This is evidence that stock code can reach the same rejection,
not a clean stock-only control or proof that modem state cannot be responsible.
A subsequent three-format control was interrupted; do not count it as passed.
No new phone operations followed the user's request for offline-only analysis.

Build the optional a3_gnss_xtra_encode_test to compare a blob's real IDL encoder
with the raw 0x35 TLVs. It takes the library path and sends no QMI requests.
The optional a3_gnss_stock_xtra_test takes a matching stock GPS HAL path and
one to three existing orbit files. Unlike the encoder probe, it starts GNSS,
injects UTC/orbits and runs Samsung initialization, which may update modem
settings. Use only with authorized device testing and matching stock support
libraries in an isolated linker path. Verify that native tests have no competing modem clients. Keeping the GNSS
HAL unavailable on a running Android framework can trigger watchdog restarts;
do not use a long service blackout as a live isolation technique. Prefer a
registered HIDL service with a temporary coherent stock backend, or a native
test environment where the framework is not waiting for the service. Its
return value alone is not an orbit acceptance check.

The exact final-file rejection cause remains unproven: file validation,
time/week interpretation and modem state are still candidates. In particular,
IDL presence of a command does not prove the running handler supports it;
0x85 version-check calls fail in the saved stock/current logs despite having
an IDL entry. Neither firmware flashing nor blind NV/checksum/time changes
are justified as a demonstrated fix by this analysis.

SM-A300F RF follow-up (2026-10-22)
--------------------------------
The supplied SER BRH1 AP/BTI3 CP archive is for SM-A300F (Android 5.0.2),
not SM-A300FU.
The phone reports board Rev01 and selects the corresponding A3 EUR DTB.
All 24 modem.* / mba.mbn files in /firmware-modem/image match the supplied
BTI3 CP archive byte for byte. No CP firmware was written during this work.

In this stock libgps.utils, GNSS_RF_CONFIG points to sec_gps_conf+0x84,
whose initializer stores 1. Offset +0x88 is the next setting in this build.
The bridge does not access those private structures and already sends 1.
The stock initialization also sends AGPS mode 7, XTRA enable 1 and CERT TYPE 15;
that complete initialization did not restore reception in the controlled test.
Do not infer antenna gain or an arbitrary GPIO mapping from these parameters.

The optional a3_gnss_stack_probe drives a complete matching legacy GPS set in
standalone mode and reports modem NMEA GSV, solution mode and valid-position
callback counts, without coordinates. It takes HAL_PATH [SECONDS] [MODE].
The native current/stock/current control used 90/120/90 seconds respectively.
Maximum simultaneously measurable GPS/GLONASS SVs were 1/1 in all three runs;
GPS/GLONASS peak C/N0 was 27/32, 27/30 and 30/28 dB-Hz. No run produced a fix.
Sequential sky tests are not a calibrated receiver-sensitivity measurement.

The first attempt to use the complete stock set under Android 12 hit an NMEA
contract mismatch: Gnss::nmeaCb requires a NUL at data[length], but the stock
buffer did not have one there. The optional gps.a3_stock_test adapter copies
only that bounded NMEA payload and terminates it before forwarding callbacks.
Its backend path is explicitly diagnostic (/data/local/tmp/gnss-rf-compare).
With all five matching stock libraries and this adapter, HIDL delivered
NMEA callbacks for 120 seconds without a service crash; no fix resulted.
The stock legacy SV layout is not AOSP-compatible: its HIDL SV values from
that early adapter must not be used as satellite measurements.
The diagnostic adapter and native probe are non-installable build targets,
not product backends. Temporary mounts were removed after comparison.

The current source also used strlcpy on a length-delimited NMEA input.
Copy exactly len readable bytes and append a NUL at len; neither assume a
source terminator nor leave the declared boundary uninitialized after an
earlier NUL. a3_gnss_nmea_test exercises the real message constructor/proc
and HIDL external-string check, including a guard-page source and embedded NUL.
It is an optional non-installable target. This fixes a buffer contract;
it is not evidence of increased RF sensitivity.

A read-only snapshot of MSM8916 GPIO96 showed cfg=0x200/io=3 while GNSS was
active and cfg=1/io=0 after stop. No GPIO request, pinmux change or MMIO write
was made by the snapshot. The hardware L18 enable register was 0x80, with
ULT-PLDO voltage selection 0x4c (2.7 V), matching the stock L18 DT setting.
An AP regulator sysfs state of disabled did not mean this modem-voted rail
was physically disabled. Do not add an always-on vote or change voltage just
from that cached AP state. The FU schematic was only a circuit reference;
these runtime pin/PMIC observations were made on the F handset itself.

An uninterrupted receiver test with Wi-Fi on/off/on did not show reproducible
recovery on disabling Wi-Fi. The explicit --delete-aiding option of
a3_gnss_psds_status sends LOC 0x44 with deleteAllFlag=1 and requires both the
common QMI response and final modem indication. BTI3 acknowledged it with
status=SUCCESS; a subsequent 120-second standalone session still had no fix.
This command removes GNSS aiding data and is never sent by the default query.
It does not write factory RF calibration or EFS partitions directly.

The early native-isolation runs caused Android framework watchdog restarts
while the HAL was unavailable. Kernel boot_id did not change. Subsequent
registered-HIDL stock and fixed-production runs kept system_server stable.
The weak-reception cause remains unresolved; no speculative RF/voltage/NV
change is presented as a fix. Antenna, environment, and untested differences
from the complete stock OS remain possible. A full stock kernel/OS comparison
was not performed because the user prohibited reboots.

Build-only Soong diagnostic outputs for the current a3lte ARM variant:
  m out/soong/.intermediates/device/samsung/msm8916-common/gps/a3_gnss_stack_probe/android_arm_armv8-a/a3_gnss_stack_probe
  m out/soong/.intermediates/device/samsung/msm8916-common/gps/gps.a3_stock_test/android_arm_armv8-a_shared/gps.a3_stock_test.so
Non-installable Soong targets are intentionally not exported as installed
Make module aliases. Build a3_gnss_nmea_test by its ordinary Make module name.

SM-A300F kernel-interface follow-up (2026-10-22)
-----------------------------------------------
strace covered a fresh stock native initialization/start/stop with a registered
Android GNSS service left available, plus a stock HIDL session under the real
GNSS UID. All 14 native Qualcomm IPC Router ioctls succeeded. SoC identification
sysfs reads and the qmux_radio socket connection succeeded. /dev/smem_log is
absent because CONFIG_MSM_SMEM_LOGGING is disabled; its driver is a shared-memory
logger. /etc/qmi_fw.conf is absent in the supplied stock system image too.
This trace does not cover every optional GPS feature or the full stock RIL.

Stock libloc_eng opens /sys/class/power_supply/battery/gps on start/stop.
That node exists, but the Android 12 GNSS service got DAC EACCES (root:root 0664).
The stock OS instead runs the legacy HAL inside the system UID, and stock init
chowns that node system:radio. In sec_battery.c the write only sets EVENT_GPS;
sec_bat_temperature selects charging-temperature thresholds when event_check
is enabled. It does not control an antenna, LNA pin, RF filter or regulator.
No product permission/policy change was added for this diagnostic-only backend.

A further registered-HIDL comparison used the stock liblbs_core/libizat_core
as well as the five original GPS binaries, and temporarily allowed the GNSS
UID to write the battery flag. All temporary library mounts and node ownership
were restored afterwards. In 90 seconds there were 1195 NMEA sentences and no
fix; complete modem GSV cycles contained at most 3 positive-C/N0 GPS and
1 GLONASS, peaking at 28/24 dB-Hz. This was not a cold TTFF measurement and does
not demonstrate an improvement over the earlier sequential trials.
The optional stock adapter now drops the incompatible legacy SV callback;
its receiver measurements come from NMEA GSV, not misinterpreted SV structures.
Production SV conversion is unchanged.

A separate, real kernel mismatch was found below the HAL. The stock and current
DTs declare memshare,peripheral with a guaranteed 0x200000-byte modem GPS client.
The decompressed SM-A300F stock kernel contains that compatible string; our
driver accepted only qcom,memshare-peripheral. On the live phone the parent was
bound but qcom,client_1 had no driver. A read-only one-shot snapshot found slot 0
with nonzero physical/virtual allocation cookies, but size/alloted/guarantee=0.
This matches the legacy request handler, which allocated a DMA buffer without
recording its size/allocation state. Thus memory was allocated through the
fallback path; this is NOT proof that the modem had no memory or that this bug
caused its low C/N0.

Kernel commits 9c359bb3aa88 and 03323f6fc3ea accept the legacy compatible,
register the child driver before parent probing, advertise QMI after initial
client allocation, track legacy allocation ownership/size, bound replies to the
actual available size, and validate/free/reset non-guaranteed DMA allocations
with matching DMA attributes and allocation/free serialization. Guaranteed
buffers are retained. The host regression test extracts the real handlers and
checks reuse, size bounds, failed/zero allocations, stale handles, proper DMA
release, guaranteed retention and transport-error unlock under ASan/UBSan.
The ARM driver and full zImage-dtb build succeeded. No new kernel was flashed,
no modem was restarted, and no runtime rebinding of its in-use memory was tried.
The effect of these kernel changes on reception remains untested.
